## Historical and current mechanism inventory

Every classification below distinguishes invocation from measured effectiveness. Paths are relative to the respective repository; costs not supported by a measurement remain unknown.

### 1. Sharded checkpoint generations and compatibility reader

**ACTIVE_BUT_PARTIAL.** Original motivation: avoid the monolithic raw JSON → typed payload → live tree overlap. Anemone `031455b67e7851bbfd148363310abd41ca98f526` introduced the C2b-era writer/skeleton; `c7a85a7937c08d29e85baf22bb27f369b5c28a89` developed the incremental C2d1 path, and `675c013881d6ab5bf99ef19cefee2f512d9f6c20` the split C2e layout. The history was reviewed with the actual diffs/docs; many original commit subjects are uninformative (“ze”). C2c's `load_sharded_search_checkpoint` remains a full typed-payload compatibility/equivalence reader. Chipiron's directory path actually calls `load_search_from_sharded_checkpoint`, not that C2c reader. Retain both purposes; do not describe C2c as bounded-memory runtime restoration. Tests: Anemone `test_checkpoint_sharded.py`, Chipiron runner sharded round trips. No independent C2c memory win is established.

### 2. Split payloads, slim shells and streaming runtime batches

**ACTIVE_AND_EFFECTIVE**, with remaining CPU cost **NEEDS_MEASUREMENT**. Anemone `sharded_restore.py`, `sharded_io.py`, `node_restore.py` separate state payloads, node shells and runtime/edges. Subsequent `1e8879a687aaf16b107a297539c2c2fb8bf6d575`/`0680c9f3e703c3540d329df28c6d171686fe71c3` split the implementation into focused modules. Runtime records stream through 2,048-record batches; the completed diagnostic reports 119 batches, no retained full node-payload graph and zero restore decodes with #77. State payloads/shell maps and the final runtime are still O(N); streaming does not make the whole operation O(1). Raw batch mappings and typed batch records temporarily coexist. The approximately 190 seconds before selector restoration is the next restore CPU target. Profile existing decoder/link/evaluation boundaries on small fixtures before removing typed intermediate mappings, tuning batch sizes, or changing formats. Tests cover node-record/split, streaming/nonstreaming, topology, values, RNG and selector parity. Retain format; optimize adapters only with exact parity.

### 3. State summaries, dense payload stores, lazy anchor/delta handles

**ACTIVE_AND_EFFECTIVE** for restore. `f7ba181dc01b5ae0dca3a4f61d4a92fbaef637f6` and `3606482945536e9ba1ca042ea4ebf234d8f43d8e` developed dense stores/summary-aware restoration. Real #77 restore retains 242,680 opaque payloads without decoding any state. Tests cover dense/sparse IDs, lazy repeated reads, ancestry, missing/cyclic chains and save payload reuse. Retain; summaries do not replace full states when a legitimate operation needs one.

### 4. Checkpoint resolver versus bounded live rematerialization cache

**ACTIVE_BUT_PARTIAL; NEEDS_MEASUREMENT during Growth.** Anemone `CheckpointStateResolver._resolved_states` is an unbounded strong-reference dictionary; resolving a delta also caches its ancestors. Chipiron `_LiveCompactStateResolver` has a separate bounded `OrderedDict` (10,000 by the supplied production settings). They are different owners. Runner `_state_eviction_skip_reason` immediately skips all `CheckpointBackedStateHandle`s, including handles backed by Anemone's now-populated dictionary. Thus live eviction cannot bound restored-state retention. The #77 restore result solves unnecessary restore reads, not long-lived Growth ownership. Checkpoint save usually reuses original payloads; propagation/rollout/expansion can still request states. Live compact payloads can refer to stored parents and must survive eviction independently of decoded-cache membership. Existing resolver/eviction tests exercise reconstruction and bounded live LRU, not a long-running bound for restored nodes. Retain both implementations now; first measure unique legitimate resolves, ancestor replay depth, references and hit rates across persisted warm cycles. Do not impose an independent LRU or clear either owner blindly.

### 5. Sparse Linoo node states and heap invalidation

**ACTIVE_BUT_PARTIAL**, not bypassed. `b2606a9753119b42501d87b971ba7f144812c03b` elides the default `opened` entry; current `runtime_state.py`, `checkpoint_state.py`, `candidate_heap.py` preserve this. Per-depth accounting includes elided nodes; frontier/exact/terminal entries remain explicit. Real sparse-table count 233,681 means 8,999 entries elided (about 3.7%); most of this tree is non-default, so a small reduction is expected under this representation. Node IDs also occur in frontier sets, heap/version/signature tables and the tree. These are incremental invalidation/index structures, not duplicate decoded states. Removing them can force O(N) rescans or change stale-priority/tie behavior. Existing Linoo, alternating, cached-frontier checkpoint and RNG tests verify saved state/choice equivalence. Retain the proven sparse scheme. Measure a complete status/heap-size census on small fixtures before proposing compact storage; the diagnostic sample alone does not prove a cheaper representation preserves updates.

### 6. Lazy evaluation runtime slots

## Ranked opportunities and bounded scope

1. Repair committed-cycle warm reuse: avoids approximately 202 seconds of repeated restore per comparable gen38 cycle **as a hypothesis**, and avoids overlapping runner-owned trees. Prove on small fixtures; preserve unsaved-cycle behavior and evaluator-version semantics.
2. Shared bounded sharded snapshot reader with disk-backed family context: Dataset first, Reevaluation second. Removes whole-snapshot residency without inventing new targets; medium implementation/risk.
3. Mapped tensor-cache/bounded construction path: potentially removes complete-cache CPU copies and list/stack peaks; preserve global schedule, optimizer/resume and diagnostics. Benefit requires CPU/CUDA peak measurements.
4. Small atomic heavy-phase resource leases: maintain independent workers and overlap cheap phases; reject/defer loads whose incremental peak budget is not reserved. Base budgets on measurements, not worker names.
5. Profile the remaining restore adapters and save/export temporaries, then optimize existing paths. In parallel measure long-lived resolver ownership before any cache cap. Changing checkpoint formats or replacing languages is not the first response.

## Warm reuse contract and behavior review

The first implementation supports only a live runtime saved by this runner and subsequently acknowledged by successful Growth run-state publication. Compatibility must include committed generation/checkpoint identity, input run state, active model artifact and bundle contents, force override, effective runtime config, pending patch/cursor, live node/branch counts, evaluator version, search/rollout RNG state, and current mutation/save state. Model path equality alone is insufficient. Foreign/external run-state advancement must refuse rather than publish stale Growth. An interrupted save/export/manifest/run-state publication never arms reuse.

The warm path must preserve the existing attach-without-reevaluation call for an unchanged active bundle: Anemone `set_evaluator` increments evaluator version even with identical weights. Omitting that call would change checkpoint/evaluation versions. Changed evaluator/force/config or patch transitions use the cold reference path; unsupported config continues to fail the existing validator. A worker restart has no warm eligibility and restores normally. Eligible warm reuse preserves the eviction/rematerialization owner and hot-set state; it does not call `_reset_growth_state_eviction_runtime` or reinstall phase wrappers. Eligibility currently requires eviction policy `none` and single-step (non-rollout) expansion. Native selector checkpoint rebind is retained to reproduce cold selector cache versions exactly; it is O(N) in selector metadata and does not reconstruct a second tree. Identity/observability adds no tree census.

No-save cycles deliberately remain cold on the next cycle, including unsaved node/value/RNG changes. This preserves the current potentially undesirable loss of unsaved Growth. A separate reviewed behavior correction could retain it, but this PR must not claim that change is scientifically equivalent. The bounded warm scope is persisted compatible cycles, not arbitrary live-object existence.

## Implemented correction and explicit production gate

The isolated branch adds an optional three-hook Growth lifecycle (`load_growth_runtime`, pre-publication validation, post-publication acknowledgement); other runners keep their old protocol. The tracker owns filesystem/content identities and bounded scalar/RNG stamps, never tree references. `load_or_create` remains explicitly cold and now drops runner-owned graph references and collects wrapper cycles **before** constructing a replacement. Direct callers retain cold semantics.

Warm reuse requires this runner’s completed checkpoint write and the successful enclosing generation/run-state publication. Unchanged checkpoint identity covers canonical path, manifest content, declared-member completeness and file inode/size/mtime/ctime; evaluator identity additionally hashes every bundle file’s contents. Run-state, active-model pointer, control, reevaluation cursor/pending patch, force override, config, counts, evaluator version and both RNGs must agree. Changed model/config/force/checkpoint/cursor/patch transitions restore; detected external run-state drift refuses before loading or publication. These checks do not implement a transaction/lease for multiple concurrent Growth publishers; the production architecture still has one Growth owner.

A strict small-fixture test initially found differing Linoo heap-entry versions. No version field was removed or normalized. Reusing Anemone’s native `StatefulNodeSelector` checkpoint export/restore hook on the existing tree reproduces the cold cache rebinding, including version tokens, while preserving selection-step count. An unchanged model is still attached each cycle, preserving Anemone’s evaluator-version increment. Unsupported selector hooks take the cold path. The hook has an O(N) selector-metadata cost; it is not a full tree restore and is included in measured runtime-load time.

**Production limitation:** with `frontier_cold` / `delta_when_safe` active, retaining the existing live handles failed exact checkpoint parity. In the retained failed fixture, node 30’s representative parent changed from cold parent 1 to warm parent 2; nodes 105/106 used warm deltas versus cold anchors. Node tags, values, priorities, choices and RNG matched in that fixture, but that does not satisfy the required exact state-reference/provenance contract. The draft therefore explicitly logs `state_eviction_requires_cold_restore` and restores whenever eviction is enabled. A separate independent-rollout fixture also found a node-shell representative-parent difference, so it logs `rollout_requires_cold_restore` and stays cold too. The strict full-checkpoint assertion remains for these cases and passes through the cold fallback. The supplied production `frontier_cold` configuration (and any rollout-enabled configuration) **does not gain repeated-restore elimination from this draft**. No production readiness or 16 GB stability claim is made.

The next warm-runtime prerequisite is an Anemone-owned saved-state-handle rebinding lifecycle: use its existing payload stores/resolver/handle constructors to adopt persisted parent/anchor identities on the same graph, without a second runtime, no eager states, and no duplicated Chipiron resolver logic. First prove exact checkpoint/export references, selector/RNG/patch semantics and eviction-owner continuity across saved cycles and interruptions. Only then remove this cold gate in a separate review. Do not impose an LRU or change checkpoint format as a shortcut. No Anemone change is included here.

No-save cycles still discard unsaved Growth on the next cold load. Save/export/manifest/run-state failures do not arm reuse; a fresh worker restores the previous committed checkpoint. Existing RAM guards and monolithic candidate-load forecasting run before the optional lifecycle. Monolithic candidates can still incur a full validation payload load even on an otherwise warm cycle; sharded checkpoints avoid it. Published generation pruning and evaluator/patch application policy are unchanged.

The draft does not repair pre-existing publication durability: ordinary run-state writes use `write_text`; the ordinary patch consumer deletes before Growth checkpoint commitment; producer `_save_reevaluation_patch_exclusive` uses `open("x")` followed by JSON writes, so exclusive creation alone does not guarantee atomic complete visibility. A dedicated publication/journal PR must test those crash/concurrency boundaries before promising exactly-once asynchronous recovery. This should precede real distributed validation, alongside measured admission leases.

## Reproducible validation and synthetic evidence

The benchmark tool is `scripts/benchmark_morpion_warm_growth.py`. It accepts no historical-run input: it generates only system-temporary fixtures, caps requested trees at 10,000 nodes/cycles at 10, uses child timeouts, verifies clean Anemone PR #77 SHA/import paths, and compares every decompressed scientific checkpoint field plus selected-node sequences. It normalizes JSON formatting only; no scientific/cache/state-reference fields are dropped. Fresh processes separate preparation, cold and warm measurement; the reference is the corrected runner forced to restore, so both modes receive the old-graph release fix. Results retain boundary RSS, process-lifetime RSS peak, available RAM, per-cycle/load/Growth/save/export timings, and eviction metrics from the existing instrumentation. Optional auxiliary mode times bounded CPU stage functions, not worker daemons.
